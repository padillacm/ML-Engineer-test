# Design

## Context

Blocks 1-4 delivered the core behind ports: `ExtractNames(ocr, recognizer, threshold)(pdf, requested, language)`, `IngestDocument(ocr, embedder, store, chunking, batch_size)(pdf) -> IngestResult(document_id, chunks_stored, already_indexed)` and `AskQuestion(embedder, store, llm, threshold, top_k, max_chunks, max_context_chars)(question) -> Answer(text, sources)`, with adapters whose config dataclasses already validate every value (`ConfigurationError`). Errors carry a code from the closed `KNOWN_CODES` and one of five categories. The image `docintel-test` has Tesseract, both models (offline) and the env vars `NER_MODEL_PATH`, `EMBEDDING_MODEL_PATH`, `EMBEDDING_MODEL_REVISION`; `docker-compose.test.yml` adds Qdrant. Versions locked today: FastAPI 0.162, Starlette 1.10, Pydantic 2.14, Uvicorn 0.54. Agreed with the user: `MAX_UPLOAD_MB=20`, `MAX_PAGES=50`, Docker as the main way to run, security hardening of prompts and retrieval in a later pass.

## Goals / Non-Goals

**Goals:** a thin, fully validated HTTP edge; one settings object; one composition root; consistent error bodies and statuses; JSON logs with request ids and no personal data; bounded concurrency; HTTP end-to-end tests in the container; evidence that the HTTP path returns exactly what the use cases return and costs little.

**Non-Goals:** runtime image and `docker-compose.yml` with Ollama (block 6); audit viewer (block 7); authentication, per-client rate limiting, prompt-injection defences (security pass / future work); async rewrites of the adapters.

## Decisions

### D1. Settings with `pydantic-settings`, mapped onto the existing adapter configs

One `Settings(BaseSettings)` in `app/settings.py`, flat environment names without prefix (the image already uses `NER_MODEL_PATH`, `EMBEDDING_MODEL_PATH`, `QDRANT_URL`, `LLM_BASE_URL`), `.env` read when present, unknown variables ignored, `SecretStr` for `LLM_API_KEY` and `QDRANT_API_KEY`. Settings only parse and range-check types; the adapter config dataclasses stay the single source of the detailed rules, and the composition root converts a `ConfigurationError` into a start-up error that names the variable. Groups and defaults:

| Group | Variables (default) |
|---|---|
| Models | `NER_MODEL_PATH` (required), `EMBEDDING_MODEL_PATH` (required), `EMBEDDING_MODEL_REVISION` (required), `TORCH_THREADS` (2; replaces `NER_THREADS` and `EMBEDDING_THREADS`, which now stop start-up, D10), `NER_POOL_SIZE` (8, D10), `EMBEDDING_BATCH_SIZE` (16) |
| OCR | `OCR_DPI` (200), `OCR_WORKERS` (min(4, cpu)), `OCR_TIMEOUT_S` (60), `OCR_FLATTEN` (true), `MAX_PAGES` (50) |
| Matching | `MATCH_THRESHOLD` (0.90) |
| Chunking | `CHUNK_SIZE` (800), `CHUNK_OVERLAP` (0.12) |
| Retrieval | `RAG_THRESHOLD` (0.808), `RAG_TOP_K` (5), `RAG_MAX_CHUNKS` (3), `RAG_MAX_CONTEXT_CHARS` (6000) |
| Vector store | `QDRANT_URL` or `QDRANT_LOCATION` (one required; `:memory:` only by explicit choice), `QDRANT_API_KEY`, `QDRANT_COLLECTION_PREFIX` (chunks), `QDRANT_TIMEOUT_S` (10), `QDRANT_ATTEMPTS` (3), `QDRANT_DEADLINE_S` (20) |
| LLM | `LLM_BASE_URL` (unset = no model), `LLM_MODEL`, `LLM_API_KEY`, `LLM_CONNECT_TIMEOUT_S` (5), `LLM_READ_TIMEOUT_S` (60), `LLM_TOTAL_TIMEOUT_S` (90), `LLM_ATTEMPTS` (3), `LLM_MAX_TOKENS` (512) |
| Limits | `MAX_UPLOAD_MB` (20), `MAX_NAMES` (1000), `MAX_CONCURRENT_JOBS` (12, measured in D7 and D10), `MAX_CONCURRENT_QUESTIONS` (16, D10), `BUSY_WAIT_S` (10, derived in D7, at most 300), `READINESS_TIMEOUT_S` (2, at most 30) |
| Logging | `LOG_LEVEL` (INFO), `LOG_FORMAT` (json \| text), `LOG_EXCEPTION_MESSAGES` (false, D10) |

Alternative: reading `os.environ` by hand (no dependency) — rejected: it re-implements typed parsing, `.env` loading and secret masking that `pydantic-settings` (same maintainers as Pydantic, pure Python, depends only on Pydantic and `python-dotenv`, both already locked) gives for free, and it is the convention FastAPI documents. Requiring the model paths instead of defaulting to the image paths keeps a misconfigured host from silently starting without models.

### D2. Composition root and lifespan

`app/bootstrap.py` has `build_container(settings) -> Container` (a frozen dataclass with `extract`, `ingest`, `ask`, readiness probes and a `close()`), the only place that imports adapters. `app/main.py` has `create_app(settings=None, container=None)`: with no container, the lifespan builds it from `Settings()` and closes it on shutdown; tests pass a container of fakes. `app = create_app()` is the Uvicorn target. Handlers get the use cases through small FastAPI dependencies reading `request.app.state.container`, so routers never import a concrete class. Models load at start-up (e5 ~5 s measured in block 4; NER start-up time measured in task 8.3), not on the first request; one process holds one copy (scaling is by processes/replicas, block 6 and `DESIGN.md`).

Without `LLM_BASE_URL` the container gets an `UnconfiguredLLM` (an application-level `LLMClient` that raises `DependencyUnavailable("llm_unavailable", "no language model is configured")`), so `/api/ask` still refuses low-relevance questions without a model and answers 503 only when it would call it. If Qdrant is down at start-up the service still starts (liveness 200, readiness 503) and the store's per-call `ensure_collection` recovers once it comes back.

### D3. Async handlers, blocking work on dedicated thread limiters

The work is CPU-bound and the adapters are synchronous and thread-safe (OCR serialises PDFium and runs Tesseract processes; NER and e5 hold a lock per instance; httpx clients are thread-safe). The extract, ingest, ask and readiness handlers are `async def`; their blocking work runs through `anyio.to_thread.run_sync` on dedicated `CapacityLimiter`s held by `JobLimiter` (jobs: `MAX_CONCURRENT_JOBS` threads; questions: `MAX_CONCURRENT_QUESTIONS` threads, 16; readiness: 2), so none of it competes for AnyIO's default 40-thread pool, which the framework itself uses. Each job gets a per-request `Cancellation`, cancelled by a task that awaits `request.receive()` for `http.disconnect` once the form is read. Rejected: sync `def` handlers (first implementation: a waiting request held a pool thread and, beyond 40, requests queued unbounded before reaching the limiter; the review measured 503s after 4x `BUSY_WAIT_S` and readiness at 7.9 s); `run_in_executor` (does not copy context variables such as the request id, and cancellation does not wait for the thread).

### D4. Upload handling

`python-multipart` parses the form (Starlette spools files above 1 MB to a temporary file and closes it when the request ends; the handler also closes it in `finally`). An ASGI middleware applies a per-route body limit: `/api/extract` and `/api/ingest` accept `MAX_UPLOAD_MB` + 1 MiB + 64 KiB: Starlette's per-field limit (`max_part_size`, 1 MiB, the one FastAPI uses; a test keeps them equal), so any `names` field the parser accepts fits (the review found a legal 1,000-name list larger than a flat 64 KiB allowance), plus 64 KiB for boundaries, part headers and `language`; every other route, `/api/ask` included, accepts 64 KiB (a 2,000-character question fully escaped is about 24 KB). Paths are matched ignoring `root_path` and trailing slashes. A declared `Content-Length` over the limit, or with more than 18 significant digits, gets 413 before the body is read; streamed bodies are counted and aborted with 413 at the limit; a non-numeric `Content-Length` is left to the byte count. After an early 413 the response is sent with only its end held back and the body is drained while it stays within `DRAIN_LIMIT_BYTES` (1 MiB) over the limit, for at most `DRAIN_TIMEOUT_S` (5 s, nginx's `lingering_timeout`); a declared length further over is not drained, nor is a client that sent `Expect: 100-continue` before its body has started arriving (refused on its declared length, it was never told to continue); every early 413 carries `Connection: close`, so the server closes the connection once the response is complete instead of reading the rest of the body itself to keep it alive. The handler then reads at most `max_bytes + 1` from the file, so the exact limit applies to the PDF itself. Content checks live in the domain (`app/domain/uploads.py`, pure: `validate_pdf_bytes(data, max_bytes)` -> `empty_file`, `too_large`, `not_a_pdf`). The header is accepted within the first 1,024 bytes, the tolerance of Acrobat and PDFium (a stricter offset-0 check would reject files PDFium reads). The declared content type and file name are ignored. Page count is checked by the OCR adapter right after opening the document (`TesseractOcrConfig.max_pages`), since only PDFium can count pages and no new port is needed.

### D5. One error mapping

`app/api/errors.py` holds a `dict[code, status]` built from the category defaults plus the overrides in the `http-api` spec, and two exception handlers: `ServiceError` -> mapped status, `RequestValidationError` -> 422 with `code: invalid_request` and a `detail` list of `{type, loc, msg}` entries (FastAPI's `input` and `ctx` are dropped, since they echo the rejected question or file bytes). Any other exception becomes 500 `internal_error` in `RequestContextMiddleware`, the outermost middleware; no `Exception` handler is registered because Starlette would run it outside that middleware, where it is unreachable. A failure after the response has started is re-raised to the server, which logs it once, redacted. 503/504 carry `Retry-After` (5 s for dependency failures, `BUSY_WAIT_S` for `service_busy`). A test iterates `KNOWN_CODES` and fails on a missing mapping. `invalid_configuration` raised during a request is a server bug, so 500 although its category is invalid input. `names` and `language` are parsed in the router from form strings into domain values (`NamePair`, a supported code) with errors `invalid_names` / `unsupported_language`, so form-field problems use the same body as every other error.

### D6. Response details

- Ingest: `status` is `indexed` or `already_indexed`; `document_id` is added through `IngestResponseOut(IngestResponse)` in `app/api`, leaving `schemas.py` byte-identical (its hash test stays). Reason for the field: the client can refer to the document, and duplicates are visible.
- Extract: `extracted_names` keeps every occurrence in reading order (one box per occurrence, as the README asks); `fuzzy_matches` one entry per distinct extracted name and requested name at or above the threshold, as the use case returns.
- Ask: answer and sources as returned; a refusal is a 200 with the fixed refusal text and no sources (a valid answer, not an error).
- Readiness: `GET /health/ready` answers `{"status": "ready" | "not_ready", "checks": {"vector_store": "ok" | "unavailable", "llm": "configured" | "not_configured"}}`, 503 when a check is `unavailable`; only the vector store is contacted (`QdrantVectorStore.ping()`); each check runs on its own 2-thread limiter with a `READINESS_TIMEOUT_S` (2 s) timeout, and a check that times out is `unavailable`; the store's ping uses a probe client with that timeout (qdrant-client rounds it up to whole seconds).
- Routes: the `extract` and `rag` routers carry `prefix="/api"` themselves, so the route template in the access line is the full path (`/api/extract`).
- `language`: a blank form value means no hint, like an absent field.

### D7. Back-pressure with a measured default

An `anyio.Semaphore(MAX_CONCURRENT_JOBS)`, awaited on the event loop under `anyio.fail_after(BUSY_WAIT_S)`, guards extract and ingest before the PDF is read into memory (form fields are parsed first, so invalid `names` never wait); a timeout raises `DependencyUnavailable("service_busy")` -> 503 with `Retry-After`. Waiting requests hold no thread, so 503s arrive after about `BUSY_WAIT_S` at any load (review probe: 120 requests, limit 1, 3 s wait -> 119 x 503 in 3.00-3.05 s, readiness 0.00 s). Without it, 40 pool threads could each hold a rendered document and fight over 4 Tesseract workers and one NER lock, growing memory and latency without bound. The default is chosen by measurement in the container (task 8.2): throughput and p50/p95 latency of `/api/extract` on the synthetic sample with 1, 2, 4, 8 and 16 concurrent clients and limits 1, 2, 4; the smallest limit within 5 % of the best throughput wins (lower latency, lower memory). Result (`docs/BENCHMARKS.md` 13.2): throughput was still rising at 4, so the grid was extended to 8 and 16; 8 gives 47.7 docs/min, 4 is 11 % below and 16 is no faster, so the first default was 8 on the 16-CPU measurement host, limited by the per-process NER lock. With the NER pool (D10) the same method gives 87.9-91.2 docs/min at 12 jobs against 78.9 at 8 and no gain at 16 or 24, so the default is **12** (`docs/BENCHMARKS.md` 15); the bottleneck is now CPU shared by Tesseract and NER. `BUSY_WAIT_S` is **10 s**, about one job's duration at full load (p50 10.1 s), derived rather than optimised. Questions take no job slot; they have `MAX_CONCURRENT_QUESTIONS` (16) slots of their own, awaited the same way (`BUSY_WAIT_S`, then 503 `service_busy`), and as many threads (embedding one query is ~20 ms; the LLM wait is I/O), so slow answers cannot starve jobs or readiness. `BUSY_WAIT_S` is capped at 300 s.

### D8. Logging with the standard library

`app/observability.py`: a JSON formatter (`json.dumps` of timestamp, level, logger, message, `request_id` and an `extra` allow-list of fields), a `contextvars.ContextVar` for the request id set by a middleware, `configure_logging(level, format)` called once at start-up (Uvicorn's own access log disabled in favour of ours, its error log kept). Each use case logs one outcome line with numeric fields only (`extraction completed`, `ingestion completed`, `question completed`: sizes, counts, stage timings, refusal reason), and the middleware logs one access line per request (method, route template, status, duration; `unmatched` for a request rejected before routing, such as an early 413); routers do not log. Exceptions are logged redacted: type names and frames (file, line, function), without messages, notes or source lines (a probe showed a literal in the raising line leaking a credential), with chained and grouped exceptions included and a core error's code kept. This applies to every handler using the service formatters, Uvicorn's error log included; `LOG_EXCEPTION_MESSAGES=true` renders standard tracebacks (messages, source lines) for local debugging. `httpx` and `httpcore` log from WARNING up, so their per-request lines with full URLs are not written. A test sends documents and requests with known names and asserts they appear in no captured log line. Rejected: `structlog` / `python-json-logger` (a dependency for ~40 lines of code).

### D9. Architecture guard extended

The existing import scanner (`tests/architecture/scan.py`) gets a rule for `app/api` (allowed third-party imports: `fastapi`, `starlette`, `pydantic`, `anyio`): forbidden `app.adapters`, `torch`, `transformers`, `qdrant_client`, `httpx`, `pypdfium2`, `PIL`, `numpy`. `app/bootstrap.py` and `app/main.py` are exempt. `app/services/` is deleted and the ruff/mypy exclusions for `app/api`, `app/main.py` and `app/services` are removed; `app.api.*`, `app.main`, `app.bootstrap`, `app.settings` and `app.observability` join the strict mypy override and the coverage sources.

### D10. Fixing what the review and the evidence left open

The first pass listed P4-P10 in `docs/KNOWN_LIMITATIONS.md`; most are fixable within the stack, so they are fixed here, and only what the stack really prevents stays listed.

- **NER throughput (P4)**: `TransformersNameRecognizer` keeps a pool of `NER_POOL_SIZE` (default 8) token-classification pipelines sharing one model and one tokenizer: the tokenizer steps (tokenising a text, grouping tokens into entities) run under one lock, and the forward passes run in parallel, each with `TORCH_THREADS` intra-op threads (process-wide, shared with the embedder: the review found that two per-model settings could not both hold, so they were merged; start-up warns when `NER_POOL_SIZE` x `TORCH_THREADS` exceeds the CPUs available from affinity and cgroup v2 `cpu.max`); a warm-up call at load fixes the tokenizer's truncation and padding settings, so later calls only read it. Measured (BENCHMARKS 14): spans identical to pool 1 on all 60 sample documents under 16 threads, NER-only throughput 66 -> 186 docs/min at pool 4 x 2 threads, +67 MB after warm-up. End to end (BENCHMARKS 15) pools 4 and 8 are within 4 % on short documents, but on 50-page documents pool 4 is 6.8 % slower and under mixed load pool 8 halves the short-document p95 (15 s against 27-33 s), so the default is 8 (+40-90 MB). Rejected: several Uvicorn workers (each loads every model, about 2 GB per process); a tokenizer per pipeline (about 270-300 MB each for XLM-R's 250,002-token vocabulary; pool 4 measured +893 MB); dropping the lock (kept as a safeguard: an unlocked shared tokenizer gave 0 errors in 333 concurrent calls once its settings were constant, but transformers does not document it as thread-safe).
- **Abandoned jobs (P5)**: a `Cancellation` token (`app/domain/cancellation.py`, a `threading.Event`) is created per extract or ingest request; the edge sets it when the client disconnects, and the use cases and the OCR engine check it between pages (and before each embedding batch), raising `ProcessingFailed("request_cancelled")`, logged with status 499 (the client is gone). The token is checked before each page is rendered, before each page is handed to Tesseract, before the NER of each page, after OCR, before each embedding batch and before the upsert (never interrupted, so a cancelled ingest never leaves a partial document). Running Tesseract processes are stopped at once: a watcher per running page polls the token every 50 ms and sends SIGTERM to the process group, then SIGKILL after 0.5 s, while the runner's `communicate` reaps it; a cancelled job always raises, even when every page was read. Measured cancel-to-raise latency with real Tesseract: 4-223 ms against 0.78 s per page (the upper end is a page render in progress). In-process steps (PDFium rendering, an NER page, an embedding batch) still finish: Python threads cannot be interrupted. One line, `extraction cancelled` / `ingestion cancelled`, replaces the outcome line of a job stopped by its token. A `receive` that raises counts as a disconnect, and cancelling the request's task (Uvicorn's shutdown after its graceful timeout) cancels the token too, so a long job no longer holds the shutdown; a request cancelled before any response is logged 499. Rule: a request ends as 499 `request_cancelled` whenever its client had left by the time its outcome was known (including a job that completed and a wait for a slot that timed out), except a job that failed on its own, which keeps its 5xx; a completed job still logs its outcome line.
- **Declared page count (P6)**: one rule for every document. A page is checked with `FPDF_GetPageSizeByIndexF` (pypdfium2 `PdfDocument.get_page_size`), which finds the page in the tree exactly like `FPDF_LoadPage` and computes the same displayed size (boxes and `/Rotate`, inherited ones included; equal in 34 box/rotation cases) but does not parse the content stream. When the declared count is over `MAX_PAGES`, page index `MAX_PAGES` is checked first; if it exists, the document is refused with `too_many_pages` ("more than N pages"). If it does not, the last declared page is checked; if that exists, a missing page is followed by a readable one, so the document is `pdf_unreadable` (as without a limit), never cut to its first `MAX_PAGES` pages. Then pages 0 to min(declared, `MAX_PAGES`) - 1 are checked: at most `MAX_PAGES` + 2 lookups, about 0.5 ms for 50 pages whatever their content (loading them cost about 3 ms for 50 plain pages and 0.8 s per page whose content decodes to 27 MB). The document is the run from page 0 to the first missing page; a page that exists after a missing one means a damaged middle page, `pdf_unreadable`. Trailing missing entries are dropped, since PDFium cannot tell them from an overstated `/Count`; so is a longer document whose page `MAX_PAGES` and last declared page are both missing.
- **Early 413 (P7)**: after sending an early 413, the middleware reads and discards the body while it stays within `DRAIN_LIMIT_BYTES` over the route limit (an early 413 has read nothing, so the remaining body is all of it) within `DRAIN_TIMEOUT_S`, so a client that is still sending can read the response instead of seeing a reset; bigger bodies are still cut (as nginx does). Measured on Linux: with `Connection: close`, Uvicorn resets a connection closed with unread data; on keep-alive it read and discarded the rest itself, of any size (10^15 declared: 20 GB accepted in 8 s) and for as long as the client dripped it, so every early 413 now sets `Connection: close`: a far-over body is closed after about 1 MiB, a slow drip at `DRAIN_TIMEOUT_S`, and a near miss still reads its 413.
- **Questions (P8)**: questions get the same treatment as jobs: at most `MAX_CONCURRENT_QUESTIONS` at once, waiting up to `BUSY_WAIT_S` on the event loop, then 503 `service_busy`. The readiness probe pings with its own short client timeout (`READINESS_TIMEOUT_S`), so a timed-out check's thread ends within that time instead of the store timeout.
- **Exception messages (P9)**: `LOG_EXCEPTION_MESSAGES=true` (default false) logs exception messages for local debugging; the redacted form stays the default.
- **Names budget (P10)**: `first_name` and `last_name` are at most `MAX_NAME_CHARS` (100) characters each (`invalid_names` otherwise), and the upload envelope allowance is the multipart parser's per-field limit (1 MiB) + 64 KiB, so no form the parser accepts is cut by the body limit.

## Evidence plan (calibration of this block)

No model behaviour changes, so acceptance is parity and cost:

1. **Parity**: the 60-document sample through HTTP (`TestClient` on the real container) against the direct use cases: extracted names, boxes and matches byte-identical; ingest chunk counts and document ids identical; retrieval with a scripted LLM returns identical sources. Expected 100 % identical.
2. **Overhead**: median HTTP + multipart + validation time per request against the direct call (expected well under 1 % of the ~1 s per page of OCR).
3. **Concurrency default**: D7 measurement, reported as a table in `docs/BENCHMARKS.md`.
4. **Resources**: open file descriptors, temporary files and RSS before and after 200 mixed requests (half invalid) — stable.

## Deferred to the security pass

- Hostile PDF page content: a 66 KB file whose content stream decodes to 27 MB of operators renders one page in about 33 s inside the PDFium lock, which blocks other jobs' PDFium work and cannot be cancelled (page checks no longer parse content, D10). Options: a killable render subprocess with a timeout, or a cap on decoded content size.

## Risks / Trade-offs

- [A client that disconnects mid-job] -> the job is cancelled between pages (D10); the step in progress finishes and the slot is freed when its thread returns.
- [One process holds ~2.5 GB of models] -> scale by processes or replicas, not threads (block 6, `DESIGN.md`).
- [`service_busy` under bursts] -> clients retry after `Retry-After`; capacity sizing in `DESIGN.md`.
- [The 1,024-byte header tolerance accepts files with leading junk] -> PDFium decides whether they open (`pdf_unreadable` otherwise).

## Migration Plan

`app/services/` and the skeleton routers are replaced; the HTTP contract is unchanged. `AskQuestion` now raises `InvalidInput` instead of `ValueError` for a blank question; its tests follow.
