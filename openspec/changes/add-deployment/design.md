# Design

## Context

Blocks 1-5 delivered the service: OCR, NER and matching, the RAG chain behind ports, and the HTTP edge with settings, back-pressure, cancellation and observability. Everything was verified in a `test` image (`base` + dev dependencies) with `docker-compose.test.yml` (Qdrant on an internal network, tmpfs storage). The language model was always a scripted fake or a stub; `UnconfiguredLLM` answers 503 `llm_unavailable` when no model is set. Host: Windows 11, Docker Desktop (WSL2) with the GPU visible to containers (`--gpus all`, `/dev/dxg`), RTX 4070 Ti 12 GB, 16 logical CPUs, 32 GB RAM.

## Goals / Non-Goals

**Goals**: one command to start a production-like stack (`docker compose up`), with or without a local GPU model; an image without test or development code; measured language-model choice, answer quality and latency; measured throughput of the deployed stack for `DESIGN.md`.

**Non-Goals**: orchestration beyond compose (Kubernetes, autoscaling), TLS termination and authentication (a reverse proxy's job; noted in `DESIGN.md`), the audit viewer (block 7), security hardening of ingestion, prompts and retrieval (deferred pass), fine-tuning or prompt redesign (the prompt is fixed by block 4; only a measured defect would reopen it).

## Decisions

### D1. Runtime stage on top of `base`

`FROM base AS runtime`: `uv sync --frozen --no-dev --no-install-project` for dependencies (cache mount, as in `test`), then only `app/` is copied (no `tests/`, `sample_pdfs/`, `pyproject` dev extras), `uv sync --frozen --no-dev` installs the project, `USER app`, `ENTRYPOINT ["/usr/bin/tini", "--"]`, `CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--http", "h11", "--timeout-graceful-shutdown", "30", "--no-server-header"]`. Uvicorn's own access log is already replaced by the service's (block 5 D8). One worker per container: every worker loads every model (about 2.3 GB RSS), so scaling is by replicas, not `--workers`. `--http h11`: block 5 measured that httptools hides a client's disconnect when a second request is pipelined (P5) at about 10 % more edge cost per request, irrelevant next to seconds-long jobs. `HEALTHCHECK` runs `python -c` with `urllib` against `/health/ready` (the slim image has no curl; installing one adds a package for a probe). Alternatives: a distroless final image (no shell for Tesseract's process group handling and harder debugging; the base already pins Debian and apt versions), multi-worker Uvicorn (rejected above).

### D2. Compose stack and profiles

`docker-compose.yml` services: `app` (`build: target: runtime`, `image: ${APP_IMAGE:-docintel}`), `qdrant` (v1.20.0 digest shared with the tests, named volume `qdrant_data`, readiness healthcheck as in the tests, not published), and under profile `gpu`: `ollama` (pinned `ollama/ollama` version and digest; `deploy.resources.reservations.devices` for one NVIDIA GPU; named volume `ollama_models`; `OLLAMA_CONTEXT_LENGTH`, `OLLAMA_NUM_PARALLEL`, `OLLAMA_KEEP_ALIVE` from the measurements; healthcheck with `ollama list`) and `ollama-pull` (same image, `ollama pull ${LLM_MODEL}` against the server, `restart: "no"`). The app `depends_on` Qdrant `service_healthy`. Start: `docker compose up -d` (no model, or a hosted one from `.env`) or, with the local model, `COMPOSE_PROFILES=gpu docker compose up -d` (D13). Alternative: a separate compose file for Ollama (two files to remember; profiles keep one). As first built, the app also depended on `ollama-pull` with `required: false` and pointed itself at Ollama when the name `ollama` resolved at its start; the review (task 8.1) showed that compose then starts the app even when the download failed, so a failed pull left a service reporting `"llm": "configured"` without a model, and that the name lookup was a guess (D13 replaces it). As built after the review: the app depends on the one-shot `llm-warmup` (no profile, `service_completed_successfully`, required), which checks the model and asks the warm-up prompt when the app uses the stack's Ollama and exits 1 otherwise, so compose does not start the app after a failed download (verified: wrong model name, failed pull, model missing from the volume, the profile without `COMPOSE_PROFILES`: `up` exits 1, the app is created but never started). A hosted model combined with the profile is not supported: `LLM_MODEL` names the model of both; `ollama-pull` checks first and exits 1 when the app is pointed anywhere but the stack's Ollama. Ollama keeps compiled GPU kernels in its volume (`CUDA_CACHE_PATH`, 4 GiB cap): measured on a 1B model, a fresh container otherwise needed 33-50 s to load plus 33-46 s of CUDA JIT before the first token, so the first question failed with 504 `llm_timeout`; with the cache and warm-up the load took 1.0 s and the first answer 1.8 s after recreating the container. The download runs in `ollama-pull`, a second Ollama server of its own on the `egress` network only, sharing the volume, and only when `ollama show` does not find the model there (a warm volume starts offline); the serving `ollama` is on `backend` only (review finding 9). The runtime image is compiled to bytecode (the non-root user cannot write `.pyc` into the root-owned venv): imports take 4.2-4.9 s instead of 8.6-9.5 s, for about 200 MiB.

### D3. Configuration through `.env`

Compose reads `.env` (variable substitution) and passes the app exactly the settings it reads, each as `NAME: ${NAME:-}` (empty means the setting's default, `env_ignore_empty`), plus a few fixed values (`QDRANT_URL=http://qdrant:6333`, the two key files, the model wiring of D13). As first built it used `env_file: .env`, which copied every variable of `.env` (another service's token, say) into the app's environment, `docker inspect` and `docker compose config` (review finding 3); `tests/deploy/test_compose_wiring.py` keeps the list equal to `app/settings.py`. A value with `$` must be single-quoted in `.env`, or compose replaces `$name` with a variable (measured: a 23-character fake key became 14 characters, with warnings naming its fragments). `.env.example` lists every variable with its default and a comment, secrets as empty placeholders. The user's OpenAI key, if any, is written by the user into `.env` (git- and docker-ignored); it never appears in the repo, the image, compose output or logs (settings mask it, block 5), nor in the container's environment (it reaches the app as a secret file, D11). `.gitignore` gets `!.env.example`. A missing `.env` must not stop the stack (every value has a default).

### D4. Networks and exposure

Network `backend` (`internal: true`): app, Qdrant, Ollama. Network `egress`: app (published port, outbound calls to a hosted model) and, after the review, only `ollama-pull` of the Ollama services (model download; the serving Ollama is on `backend` only, at a fixed address, D13). Only the app publishes a port, bound to `127.0.0.1` by default (`APP_BIND`, `APP_PORT`), because the service has no authentication; exposing it beyond the host is a decision for a reverse proxy with TLS and auth (`DESIGN.md`).

### D5. Language model choice by measurement

Candidates that fit the 12 GB GPU with the context the prompt needs: `gemma4:e4b-it-qat` (6.1 GB), `gemma4:12b-it-qat` (7.2 GB), `gemma4:12b-it-q4_K_M` (8.0 GB); optionally a hosted OpenAI model as a reference if the user adds a key. Larger Gemma 4 sizes (26B, 31B, 16-20 GB) do not fit. Tags and digests are verified against the Ollama library when pulled and recorded. Rule: among models whose answer accuracy is within the 95 % interval of the best local model, the one with the lowest p95 latency; a candidate whose wrong-refusal rate on answerable questions or whose answer-language mismatch is clearly worse is excluded. The hosted model is a reference, not a default (the stack must run offline).

### D6. Answer quality metric

The corpus has gold answers (`qa.jsonl`: answer string, answer page, gold sentence; 2,871 answerable questions in five languages) and 300 unanswerable questions (`unanswerable.jsonl`). On the 600-document index, through `/api/ask` of the deployed stack: answerable accuracy = normalised gold answer (NFKD, casefold, punctuation and whitespace folded) contained in the answer, with token-F1 as a secondary score; wrong refusals on answerable questions; correct refusals on unanswerable questions (split into threshold refusals and model refusals); answer language (stop-word detector of block 2) equal to the question's. A stratified sample (by language and document type) sized for a ±4-point interval; a manual audit of 50 answers scored wrong by containment checks the metric itself (paraphrases, dates and numbers in other formats) and is reported. Rejected: an LLM judge (a second model to trust and pay for; containment on short factual answers is checkable).

### D7. Throughput and resources of the deployed stack

Runtime image, compose, real models: parallel `/api/ingest` and `/api/extract` with the block 5 method (75-request runs, two passes), with the app container unlimited and limited (`cpus: 8`) to check the oversubscription warning and whether `MAX_CONCURRENT_JOBS` / `NER_POOL_SIZE` need a lower default for smaller hosts (documented as a sizing table rather than a new default if they do). Questions: questions per minute at `OLLAMA_NUM_PARALLEL` 1, 2, 4 with `MAX_CONCURRENT_QUESTIONS` 16, latency p50/p95 and VRAM; `MAX_CONCURRENT_QUESTIONS` and `LLM_READ_TIMEOUT_S` are set from it. Cold start: first `docker compose up` after a build (no page cache), model load into VRAM, first answer; image sizes (runtime against test).

### D8. Smoke tests of a running stack

`tests/deploy/` (marker `deployed_service`, skipped unless `SERVICE_URL` is set) uses only `httpx` against the live service: `/health`, `/health/ready`, `/api/extract` on `sample_pdfs/` with names (boxes in PDF points, matches), `/api/ingest` twice (`indexed`, `already_indexed`), `/api/ask` answerable (when a model is configured) and off-topic (refusal), an invalid upload (415) and the request id header. Runtime hygiene checks run with `docker run` of the runtime image in the smoke compose file: `import pytest` and `import pymupdf` fail, `id -u` is 10001, `HF_HUB_OFFLINE=1`, no `tests/` directory. `docker-compose.smoke.yml` adds a `smoke` service (test image, `SERVICE_URL=http://app:8000`, backend network) to the stack.

### D9. Fixes found by the model measurement

The measurement (`docs/BENCHMARKS.md` section 16.10) found three defects, fixed in this block rather than recorded as limitations. (1) Gemma 4 on Ollama thinks by default; through the OpenAI-compatible endpoint only `reasoning_effort: "none"` turns it off (`think: false` is ignored). Thinking cost 10-14 points of accuracy, a median model call 7.2 times longer with e4b (2.8-5.3 times with the 12B models), and 21 % of e4b's replies ended empty at the token limit, which the service turned into silent refusals. New optional setting `LLM_REASONING_EFFORT`, sent only when set; compose sets `none` whenever the app's `LLM_BASE_URL` is the stack's Ollama (a short `sh -c` before the image's command), unless `.env` sets another value; an empty reply with `finish_reason` `length` is logged as its own outcome. (2) Hosted reasoning models (`gpt-6-luna`) reject `max_tokens` and `temperature` 0 with 400: `LLM_MAX_TOKENS_FIELD` (`max_tokens` default, or `max_completion_tokens`) and `LLM_SEND_TEMPERATURE` (default true); the provider's error code (validated as a short identifier, never its message) goes into the error message, so a rejection is diagnosable from the logs. (3) Twelve simultaneous first ingestions into an empty store gave 11 x 503: concurrent `ensure_collection` calls are serialised by a lock in the store, and a create that loses a race with another process verifies the existing collection. Chosen defaults: `LLM_MODEL=gemma4:e4b-it-qat`, `OLLAMA_CONTEXT_LENGTH=8192` (largest request about 3,600 tokens; Ollama's own default on this GPU is 4,096), `OLLAMA_NUM_PARALLEL=2`, `OLLAMA_MAX_LOADED_MODELS=1`, `OLLAMA_KEEP_ALIVE=-1` (a reload takes 33-42 s), `MAX_CONCURRENT_QUESTIONS` 16 and `LLM_READ_TIMEOUT_S` 60 unchanged (60 s is about 4 times the loaded p99 at 16 concurrent questions).

### D10. Fixes found by the deployed measurement

Section 17 of `docs/BENCHMARKS.md` found three points, fixed in this block. (1) Ingestion stopped at about 50 docs/min with 4.9 of 16 CPUs busy: one e5 embedder behind one lock, 5.8 s per page under load against 0.7 s alone; questions embed their query through the same lock, so they wait behind ingestion. The embedder becomes a pool sharing one copy of the weights, like the NER pool (block 5 D10), with `EMBEDDING_POOL_SIZE` calibrated by measurement. (2) The job and pool defaults (12 / 8) fit 16 CPUs but lose 12 % of extraction at 8 CPUs and 26 % at 4: when unset, `MAX_CONCURRENT_JOBS`, `NER_POOL_SIZE`, `EMBEDDING_POOL_SIZE` and `OCR_WORKERS` are derived at start-up from the available CPUs (affinity and cgroup quota, as the oversubscription warning already reads them), following the measured sizing table and capped at the 16-CPU values; set values win. (3) Qdrant and Ollama healthchecks probed only every 5 s, so the app started about 5 s after Qdrant was ready: `start_interval: 1s` during a 30 s start period.

As built (task 6.2, `docs/BENCHMARKS.md` section 18): the e5 embedder keeps one model and one tokenizer for `EMBEDDING_POOL_SIZE` concurrent passage batches; only tokenising runs under a lock (0.3 % of a call), the forward passes run in parallel, and the vectors are bit-identical to a pool of 1 (maximum difference 0 over 780 calls). Queries get one extra reserved slot and go before waiting passages: without it a question waited for a passage batch (p50 0.3-1.2 s) or, with no priority at all, was starved for minutes; with it a query takes 53-81 ms under 12 concurrent passage streams. Unset sizes come from `concurrency_for(cpus, TORCH_THREADS)` in `app/bootstrap.py`: jobs = ceil(3/4 x CPUs) at most 12, NER pool = CPUs / T at most 8, embedder pool = CPUs / (2 T) at most 4, OCR workers = CPUs at most 4, each at least 1, giving 12 / 8 / 4 / 4 on 16 CPUs, 6 / 4 / 2 / 4 on 8 and 3 / 2 / 1 / 4 on 4. The embedder pool was calibrated end to end with the D7 rule: on 16 CPUs pool 4 (86.3 docs/min) against 70.4 for pool 2 and 84.2-85.3 for 6 and 8, against 45.8 for the former single embedder; pool 2 is the smallest in the band at 8 CPUs and pool 1 at 4.

As built (FIFO hand-off, `docs/BENCHMARKS.md` section 18.6): both pools admitted callers through a plain condition, so a thread that had just released a slot usually took it again before a woken waiter ran (with one embedder slot, some of 16 callers waited 58-61 s while one served 45 of 60 calls; formerly `KNOWN_LIMITATIONS.md` P11). `app/adapters/slots.py` (`FifoSlots`, one small helper inside the adapter layer, used by both adapters) now hands a freed slot directly to the first waiter of its queue; lanes keep the embedder's policy (queries first and allowed the reserved slot, passages at most `EMBEDDING_POOL_SIZE`, each lane in arrival order); `close()`, the error mapping and the outputs are unchanged. Measured before and after on the same request sets: throughput within the run-to-run spread (ingestion 88.6 -> 89.3 docs/min on 16 CPUs and 63.4 -> 64.7 at 8; extraction 84.0 -> 84.7 at pool 8 and 85.8 -> 84.8 at pool 4), the embedder's slowest call under 16 callers 60.7 -> 18.8 s (pool 1) and 21.6 -> 7.4 s (pool 4) with every caller served 3-5 times, and with 12 extraction jobs on 4 NER pipelines the per-job NER time per page p95 3.0-3.3 -> 2.5-2.8 s; at the default pool sizes the per-job spread of the short-document runs did not change measurably.

### D11. The language model key as a compose secret (task 7.1)

With `env_file: .env` the key was an environment variable of the app container, shown in clear by `docker inspect` and `docker compose config`. Compose now passes it as a secret: `secrets.llm_api_key_from_env` with `environment: LLM_API_KEY`, which Compose resolves from `.env` or the shell (verified with Docker 29.9.2 and Compose 5.6.1), mounted at `/run/secrets/llm_api_key` (mode 0444, root-owned, readable by uid 10001). The app's `environment` sets `LLM_API_KEY: ""` (otherwise `env_file` copies the key from `.env` into the environment) and `LLM_API_KEY_FILE=/run/secrets/llm_api_key`. Compose refuses to create a container whose environment-sourced secret has no variable (`environment variable "LLM_API_KEY" required by secret ... is not set`), and an empty variable mounts no file, so the app's secret source is `llm_api_key${LLM_API_KEY:+_from_env}`: without a key it is `llm_api_key`, the committed empty file `deploy/no-llm-api-key`, which means no key. The interpolation is only `:+` with a constant, so the key's value never enters the resolved file (`tests/deploy/test_compose_secrets.py` checks the wiring). The settings read the file through a new `LLM_API_KEY_FILE`: once at load, whitespace stripped, an empty file is no key, at most 4 KiB, UTF-8; both variables set, or an unreadable file, stop start-up naming the variable, never the path or contents. `LLM_API_KEY` keeps working outside compose.

Measured on the isolated stack with a fake key and a fake OpenAI-compatible server (`docs/BENCHMARKS.md` section 19.7): the key occurs 0 times in `docker inspect` of the app container, in `docker compose config` and in every service's logs; the environment of the app's processes holds `LLM_API_KEY=` and `LLM_API_KEY_FILE=/run/secrets/llm_api_key`; the fake server received `Authorization: Bearer <key>` (checked by hash); without `.env` the stack started with an empty secret file and readiness `"llm": "not_configured"`.

Alternatives: pydantic-settings `secrets_dir="/run/secrets"` needs no new setting, but it reads every one of the service's settings from a file of the same name (an implicit second configuration channel), warns `directory "/run/secrets" does not exist` on every start outside a container and in the host tests, gives the environment silent precedence, and cannot treat an empty file as no key or a conflict as an error without overriding its source; the `*_FILE` convention (used by the official PostgreSQL and MySQL images) is one explicit variable and testable. A `file:` secret filled by the user puts the key in a second place beside `.env`. A `configs` entry with `content:` would be printed, key included, by `docker compose config`. What remains: `docker inspect` shows the file's path, and anyone who can run `docker exec` can read the file, as on any Docker host (access to the Docker socket is root on the containers).

As built after the review (task 8.1): without `env_file` the app's environment no longer needs `LLM_API_KEY: ""`; `QDRANT_API_KEY` takes the same pattern (`QDRANT_API_KEY_FILE`, secret `qdrant_api_key${QDRANT_API_KEY:+_from_env}`, the shared empty file renamed `deploy/empty-secret`), and when it is set the compose Qdrant requires it: Qdrant's start command reads the same secret file and exports `QDRANT__SERVICE__API_KEY` inside its own process only, so `docker inspect` of Qdrant does not show it either. One reader serves both files; it removes a UTF-8 byte order mark, and a key from a file that fails a later check (characters) names the `*_FILE` variable. Measured with fake keys (`docs/BENCHMARKS.md` section 19.8): Qdrant answers 401 without the key and 200 with it, `/readyz` needs none, and neither key nor an unrelated `.env` token occurs in `docker inspect`, `docker compose config` or the logs.

### D12. Probe access lines and the image's healthcheck (task 7.1)

The image's healthcheck probes `/health/ready` every 15 s, and each probe wrote one INFO access line (about 5,800 a day per container, more under an orchestrator). The access line of a successful `/health` or `/health/ready` request (status below 400) is now written at DEBUG (`RequestContextMiddleware(probe_routes=...)`, routes from `app/api/health.py`); every other request, a failing probe (503) included, stays at INFO, next to the readiness warning naming the failed check, and `LOG_LEVEL=DEBUG` shows every probe. Alternative: telling the container's own probe apart (a header or user agent) would keep an orchestrator's probes at INFO and is spoofable; dropping the lines entirely would hide them from debugging. The image's `--start-interval` goes from 2 s to 1 s: the service is marked healthy at most 1 s after it is ready instead of 2 s; each probe is one short Python process (`docs/BENCHMARKS.md` section 19.4).

### D13. Explicit Ollama wiring at a fixed internal address (task 8.1, review finding 2)

The first wiring (`getent hosts ollama` at the app's start) had three faults: switching from a plain `up` to `--profile gpu up` did not recreate the app (its configuration had not changed), so it stayed `not_configured`; an app restarted while Ollama was down (a host reboot starts containers in any order, without compose) ran without a model until recreated; and Docker's DNS forwards a name it does not know to the host's resolvers, so with Ollama stopped a LAN host called `ollama` (or an ISP's catch-all answer) could receive the questions and document text, at start or on any later request.

Decision: (1) the profile is switched on by `COMPOSE_PROFILES=gpu` (in `.env` or the environment), the one variable compose reads both to select profiles and for interpolation; the app's `LLM_BASE_URL` is `${LLM_BASE_URL:-${COMPOSE_PROFILES:+http://<prefix>.250:11434/v1}}`, its `LLM_MODEL` gets the Gemma default only in that case (so a hosted URL without a model still stops start-up, review finding 8), and a change of profile changes the app's configuration, so compose recreates it. (2) Ollama has a fixed address, `.250` of a fixed internal `/24` (`BACKEND_NETWORK_PREFIX`, default `10.213.47`; the other containers get addresses from `.0/25` only), and the app uses the address, not a name: no lookup can leave the stack, and while Ollama is down the requests fail on the internal network (503 `llm_unavailable`) and succeed again when it is back. (3) `ollama-pull` exits 1 with a message naming `COMPOSE_PROFILES` when the profile is active but the app is not pointed at Ollama (`--profile gpu` alone), so that mistake is visible instead of a silent `not_configured`.

Alternatives: `--profile gpu` alone cannot be kept, because compose does not expose the command line's profiles to interpolation (verified: `${COMPOSE_PROFILES}` is empty with `--profile gpu`), and no other compose mechanism changes one service's environment by profile; a profile-specific app variant would start both apps (a service without `profiles` always starts); `depends_on: restart: true` restarts the app only on compose operations, not on a reboot, and still leaves the guess; checking at start that the resolved address is in an attached subnet protects only that lookup, and Docker assigns a different address after a restart when another container took the old one (measured), so pinning it fails; waiting for Ollama at the app's start when expected still needs an explicit "expected" signal, which is (1). Costs: the documented command changes (one command still, `COMPOSE_PROFILES=gpu docker compose up -d --wait`, or the line in `.env`), and the fixed subnet can collide with another network or a second copy of the stack; compose then refuses to create the network (`networks have overlapping IPv4`) and `BACKEND_NETWORK_PREFIX` moves it (`docs/KNOWN_LIMITATIONS.md` P15, P16).

Verified with a fake Ollama (an HTTP server in the app image at the same address; `docs/BENCHMARKS.md` section 19.8): plain `up` then `COMPOSE_PROFILES=gpu up` recreates the app, which reports `configured` and is answered; with Ollama stopped and the app restarted by Docker, a question answers 503 and the next one after Ollama's start 200; a decoy server reachable as `ollama` on the egress network received 0 requests (the app's `getent hosts ollama` resolved to it); `--profile gpu` alone stops at `ollama-pull` with the message; and with the real Ollama on the RTX 4070 Ti, the model copied into a new volume, the stack started in 79.5 s the first time (warm-up 63.6 s) and 17.7-17.9 s afterwards, the serving Ollama had only the internal address and no DNS for the registry, and the smoke suite passed with the model.

## Evidence plan (calibration of this block)

1. **Model choice** (D5, D6): accuracy, refusals, language, latency, tokens per second and VRAM per candidate on the stratified sample; table and choice in `docs/BENCHMARKS.md`.
2. **Context length**: tokens of the largest prompt (6,000-character context + instructions + question) for the chosen model's tokenizer; server context set with at least 25 % margin; a check that no request is truncated (Ollama reports prompt tokens).
3. **Throughput and sizing** (D7): ingest and extract docs/min, questions per minute, resources, cold start, image sizes.
4. **Parity**: the deployed stack's extraction and ingestion results on the 60-document sample equal the test-image results of block 5 (same code, different image).

## Deferred to the security pass

- Authentication and rate limiting at the edge; TLS. The stack binds to localhost until then.
- Prompt-injection resistance of retrieved context and questions with a real model (the measurement may surface examples; they are recorded, not fixed here).

## Risks / Trade-offs

- [Gemma 4 tags or digests change upstream] -> pin the Ollama image by digest and record the model digest from `ollama list`; the pull step names the exact tag.
- [GPU passthrough differs between Docker Desktop and Linux hosts] -> the `gpu` profile is optional; without it the stack still runs; README documents the NVIDIA Container Toolkit requirement on Linux.
- [A 12B model's latency is too high for interactive questions] -> the rule in D5 prefers the faster model within the accuracy interval; `LLM_READ_TIMEOUT_S` and the question limit come from measured p95.
- [Measurement of answer quality with a containment metric misjudges paraphrases] -> the manual audit in D6 quantifies it.
- [The OpenAI comparison costs the user money] -> optional, only with a key the user adds, on a small sample whose size is stated before running.

## Migration Plan

Additive: the test image and `docker-compose.test.yml` stay as they are; the runtime stage and the new compose files do not change the test workflow.
